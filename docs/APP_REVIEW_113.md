# Fraynix review and development direction — 2026-11-10

## Assessment

Fraynix has a credible local agent foundation: chat can invoke Java-owned work, the environment exposes structured state and controls, and results can be verified, retained and recovered after interruption. The valuable feature is this connection between requests, executable tools and checked outcomes. Java provides a durable runtime; the choice of language alone does not establish intelligence.

The app is still an engineering workspace with bounded capabilities. It is not yet a broadly reliable autonomous assistant. Recent successful data workflows use a deterministic Java implementation; their success must not be described as fresh LLM reasoning, model weight training or general self-improvement. Keeping those distinctions visible protects the value of the real work.

## What the system already contains

| Layer | Present role | Important boundary |
| --- | --- | --- |
| Java coordination | Durable chat tasks, goals, typed workflows, ownership, recovery and original evidence checks | A supported action must pass its current checks; a stored success cannot authorize a new effect |
| World and simulation | Native physics, persistent body identities, observations, predictions, bounded controllers and experiment memories | Simulation and calibrated measurements remain distinct; one task family does not establish general physical understanding |
| Desktop workspace | Embedded browser, canvas, project objects, chat, data/world tools and Game Lab access | Multiple mature tools still compete for attention; integrated task flow matters more than another panel |
| Creation and data | Import, analysis, actual browser tests, retained artifacts and reusable procedures | Current qualified summaries are narrow; earlier local-model drafts had real failures and costs |
| Memory and continuity | Original journals, verified reconstruction/procedure evidence, archived workflows, children and chats | Storage and scheduling limits are separate, and deliberately bounded |
| Java brain and perception | Existing runtime coordination, observations and experimental learning paths | Activity, memory or a changing numerical state is not proof of consciousness or useful learning |

This review inspected current code paths, historical contracts, the prior actual test project and live desktop screens. Edition113 freshly exercises history and data/creation workflows. It does not claim to rerun every historic physics, camera or model experiment.

## Gaps that matter most

1. **Find and understand prior work.** Before113, three long independent selectors and raw records made useful memory difficult to use. Users need the request, original outcome, connected work, result and recheck in one place. Edition113 addresses this directly.
2. **Manage saved procedures deliberately.** The current bank has32 slots. A real lifecycle needs inspectable retirement, retention of descendants and original evidence, and deliberate reactivation. Silent deletion, duplicates or an increased cap are not a substitute.
3. **Broaden complete useful tasks.** Repeated summary qualification strengthens one path but does not add a new skill family. Choose another end-to-end task with a precise verifier, then measure it on unfamiliar inputs.
4. **Measure the LLM's contribution separately.** Use a real installed local model to choose among supported procedures, explain a refusal and recover from a failed draft. Compare it against direct/simple routing; preserve failed requests, latency and resource use. Deterministic routing remains a legitimate efficient choice.
5. **Reduce interface fragmentation.** The main browser/canvas/chat view can crowd narrow screens. A single active-task overview should answer what is happening, what evidence exists, what needs attention and what to do next. Preserve access to detailed tools without requiring users to learn every edition's terminology. The live review also showed an older cancelled task card remaining pinned after restart beside a newer completed conversation; current focus needs clearer reconciliation.
6. **Improve installation and resource behavior.** Reproducible startup on the new machine, explicit Java/Ollama versions, task-level resource budgets and measured disk growth will matter more as evidence accumulates. A new process is not a clean operating-system cache.

## Proposed next phases and acceptance gates

### 114 — saved-procedure lifecycle

Add explicit retirement of eligible saved procedures while preserving their source, qualification, reports and descendant references. Keep the active32 limit. Archived procedure IDs remain readable and verifiable. Reactivation must recheck current compatibility and original evidence; no silent promotion. Test a full bank, restart between preparation and commitment, missing/corrupt originals, referenced ancestors and failed reactivation. Measure complete costs as the retained archive grows.

### 115 — one additional complete creation skill

Use a bounded data-comparison report: import two declared sources, align their stated units/time conventions, compute differences, produce an interactive chart/table and verify every result against the original rows. Preserve mismatched units, missing observations and unsupported alignment as explicit refusals. Save the whole verified procedure and test fresh datasets after restart. Final scope should be chosen from actual user needs, not an open-ended promise to create anything.

### 116 — real-model task selection and recovery

Evaluate local-model selection across supported summary, comparison and world tasks, including ambiguous and unsupported requests. Use separate held-out cases and direct-routing baselines. Record wrong tool choices, original refusal explanations, successful recoveries, total time and resource costs. A saved procedure is learned operational memory; changed model weights require a separate training/evaluation claim.

### 117 — observation to world to artifact

Connect one calibrated observation sequence to a persistent object, generate a bounded prediction, compare actual motion, create the report and retain the checked procedure. Explicitly represent scale, occlusion, uncertainty and remaining ability to correct. Test unfamiliar motion and interrupted execution. Expand geometry or controllers only when the task exposes a measured limitation.

## Design principles to preserve

- One Java-owned execution and evidence path; desktop views present it rather than creating a second authority.
- A tool performs an action. A skill completes a task through actions, checks and recovery.
- The active world, authored source, observation and prediction are distinct records with explicit lineage.
- Past success is evidence to inspect, not permission to replay. Current sources and outcomes must still verify.
- Evaluate improvement by success, useful generalization, failure recovery and complete cost; preserve failed attempts.
- Keep private worlds separate from test projects, keep frozen editions intact, and verify what was actually pushed.

The destination is an integrated local agent that can understand a request within its supported scope, act in a visible environment, check what happened, retain useful procedures and continue after interruption. A usable evidence history is a concrete step toward that destination.
