# From a collection of capabilities to a coherent agent workspace

Design contract recorded before the Mission interface implementation, November2,2026. This extends the user's Java ownership request and subsequent request for a full conceptual, production and design review. The existing application, private projects and published editions remain preserved.

The valuable foundation is the connection between persistent entities, actual actions and checked consequences. Java owns durable identity, clocks, tasks, procedures and world state. Native physics provides measured outcomes in the declared simulated environment. The browser and camera provide separately qualified observations. The canvas turns requests into executable artifacts. The witness retains what actually happened. None of these becomes more capable merely by receiving a more impressive label.

## The next design level

Use one visible **mission** to connect request, plan, source, action, verification and retained skill. A user should be able to answer: What is the agent working on? Which world or dataset did it bind? Is Java computing, waiting for a surface or requesting recovery? What actually passed? What remains uncertain? Which saved procedure can reproduce the result?

Implement the first slice in the existing timeline, with Activity and Mission views. Keep the browser left, creation/world view center and chat right. Display actual persisted Java task/child state, original source versions, real history events and saved result references. Provide actual stop/resume and result-opening actions. No second application window, invented percentage, decorative neural activity or simulated success. Read-only status remains distinct from a verified artifact task. An absent mission is an honest empty state.

Mission presentation may format observations. Java remains the planner and scheduler. Source/document text is never rendered as privileged HTML or interpreted as instructions. Opening a saved result must preserve its actual version. The new view must work at the existing1600/1100 review widths and keep task controls accessible. Its acceptance proof uses the actual Java owner, real artifact checks, cancellation/recovery and a retained recipe rather than an animated mockup.

## A unified world without erasing domain meaning

Use the existing entity/component model as a common address space. Every entity needs a stable identity, source and revision; quantities need units and a clock. A browser object has a URL/DOM/appearance, a document has structure/content, and a physical body has pose/mass/contact. A chart position is not automatically a physical location. Link these domains through explicit observations and transforms, preserving uncertainty and provenance.

The2D game, native3D scenes, measured mat plane and abstract2–16D maps can share identities and goals while retaining their own valid mathematics. Orthographic views and higher-dimensional projections are ways to inspect state. They do not establish physical depth or additional spatial axes from a single image. The existing shared runtime already provides a foundation for coordinated views rather than multiple unrelated brains.

## What dreaming should mean here

The next engineering target is a **counterfactual experiment**. Freeze a verified world revision, fork bounded candidate plans, simulate them with known parameters, compare goal error, contact, effort and protected-object drift, and retain both rejected and accepted candidates. Commit a chosen plan only against the expected world revision/hash. Compare its actual outcome with its forecast afterward. A source change invalidates the old decision.

This builds on the existing native forecasts and persistent-world transactions. It is a proposed expansion of their narrow task coverage, not a claim that arbitrary worlds, cameras or LLM behavior already have reliable predictive models. Candidate computation must have explicit CPU/GPU/time budgets and cancellation. A background heartbeat alone is not permission to actuate a scene or browse externally.

## What an evolving skill should mean

A tool acts; a skill reaches a goal through actions, checks and recovery. Extend registered versioned procedures toward typed task graphs with prerequisites, source requirements, bounded actions and postconditions. Successful execution creates a candidate reusable version. Promote it only after independent, frozen new-condition tests against a relevant baseline. Preserve failed trials and make rollback explicit.

Persistent memory and retrieval are useful inputs, not proof of improved performance. Evaluate retrieval enabled/disabled on the same held-out tasks. Measure completion, unintended actions, recovery, retained source correctness, time and effort. Training an Ollama model's weights is a separate pipeline with its own dataset, resources, evaluation and rollback; retained procedures do not establish that training.

## Production priorities

First complete the current Java ownership migration and verify real task/skill flows. Then improve the mission/evidence presentation, resource admission, deadline/reconnection behavior and offline packaging. Keep the existing loopback authentication, one project owner, current interface lease and narrow tool dispatch. The old full game editor remains preserved; normal Game Lab uses the integrated original renderer with its native window hidden.

Creation should expand around complete offline outcomes: data→analysis→interactive artifact→independent checks→retained procedure. Later compiler targets for Java/C/Go need real build/run contracts and process restrictions. Owning the high-level algorithms does not remove the need to account for the existing renderer, browser, JSON and solver dependencies. Java's suitability and performance should be established by measured workloads rather than language comparisons.

The first production proof is reproducibility: a fresh supported machine/setup, a chosen local model, a bounded request, a real checked result, a saved skill, restart and successful reuse on changed input. The next reality proof is independently annotated footage, scale/clock calibration, occlusion/lighting changes, source freshness and uncertainty coverage. Existing041 measurements and038 failures retain their exact original scope.

## Sequence and acceptance gates

1. **044 — one Java task owner and visible mission:** all active chat planning/skill scheduling in Java; actual creation, native/data task and retained reuse; source/nonce/check/version rejection; reconnect; full regression evidence; integrated Mission view.
2. **Counterfactual planning:** bounded branches of one actual world revision; independently reconstructed candidate metrics; refusal on stale state; actual chosen execution and forecast residuals. No generic-world claim.
3. **Task-graph skill compiler:** typed declarative procedures, real prerequisites/postconditions, idempotency and explicit recovery; no untrusted executable-handler installation.
4. **Measured adaptation:** frozen fresh task cases, stronger baseline, ablations, retained failures and reversible promotion. Demonstrate useful improvement after restart.
5. **Production distribution:** reproducible supported-platform installation, offline dependency manifest, resource budgets, crash recovery, real export/import and documented model requirements.

This direction preserves the user's central idea: the application's evolving work is the content. Its strength will be judged by complete, inspectable outcomes across the connected world, browser, creation and memory systems.
